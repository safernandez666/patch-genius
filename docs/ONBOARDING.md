# Connecting patch-tracker to your Wazuh

patch-tracker reads vulnerability state from **your** Wazuh deployment. Nothing ships
with the repo: no hosts, no credentials, no data. Until you complete this onboarding the
app runs in **demo mode** against synthetic data generated by `seed/generate_seed.py`.

## Requirements

- **Wazuh 4.8 or newer.** In 4.8 the Vulnerability Detector moved its output into the
  Wazuh Indexer. The old manager endpoint `GET /vulnerability/{agent_id}` on port 55000
  was removed — on 4.14.6 it returns `404`. There is no supported way to read
  vulnerability state from the manager API, so **the app must reach the Indexer.**
- Network reachability from the app to the Indexer (default port `9200`). See below —
  this is the step most deployments get stuck on.
- Optional: reachability to the manager API (default `55000`). Only used to enrich agents
  with IP / OS / connection status and to list Windows hotfixes, neither of which exists
  in the vulnerability index.

## Step 1 — pick your topology

| Topology | Indexer change needed? |
|---|---|
| **A.** patch-tracker on the same host as Wazuh | **No.** The default `127.0.0.1:9200` already works. Point the app at `https://127.0.0.1:9200`. |
| **B.** patch-tracker on a different host | **Yes.** A default Wazuh install binds the Indexer to loopback only. Follow Step 2. |
| **C.** Different host, but you'd rather not expose 9200 | No config change — use an SSH tunnel (Step 3). |

Check what your Indexer is bound to:

```bash
grep '^network.host' /etc/wazuh-indexer/opensearch.yml
```

`127.0.0.1` means only topology A works as-is.

## Step 2 — exposing the Indexer to your network

> **Read this before editing.** OpenSearch runs in *development mode* while it is bound
> to loopback. Binding to any non-loopback address switches it to *production mode*,
> which turns several startup warnings into **hard errors**. If your host does not meet
> them, `wazuh-indexer` will not start again. Verify first, then edit.

### 2a. Verify the bootstrap-check preconditions

```bash
sysctl -n vm.max_map_count          # must be >= 262144
systemctl show wazuh-indexer -p LimitNOFILE -p LimitNPROC
                                    # LimitNOFILE must be >= 65535, LimitNPROC >= 4096
grep -E '^(node\.name|cluster\.initial_master_nodes)' /etc/wazuh-indexer/opensearch.yml
                                    # discovery must be configured, or the node cannot elect itself
```

Check the systemd unit's limits, not your shell's `ulimit` — the service does not inherit
your login shell. If `vm.max_map_count` is too low:

```bash
echo 'vm.max_map_count=262144' >> /etc/sysctl.conf && sysctl -p
```

On an LXC container this is a **host-level** sysctl: set it on the hypervisor, not inside
the container.

### 2b. Back up, then edit

```bash
cp -a /etc/wazuh-indexer/opensearch.yml /root/opensearch.yml.bak-$(date +%F-%H%M%S)
```

Set the bind address in `/etc/wazuh-indexer/opensearch.yml`:

```yaml
network.host: 0.0.0.0
network.publish_host: <the IP other hosts reach this box on>
```

**Keep loopback reachable.** The Wazuh dashboard and Filebeat both connect to
`127.0.0.1:9200`. `0.0.0.0` includes loopback, so both keep working. Replacing the bind
with only the LAN address breaks them.

### 2c. Restart and verify

```bash
systemctl restart wazuh-indexer
sleep 30
curl -sk -u admin:<password> https://127.0.0.1:9200/_cluster/health?pretty
```

`OpenSearch Security not initialized.` immediately after a restart is normal — the
security index takes a few seconds to load. Retry for up to a minute before concluding
anything is wrong. You want `"status": "green"` (or `"yellow"` on a single node with
replicas configured).

Then confirm the rest of the stack survived, and that the port is reachable remotely:

```bash
systemctl is-active wazuh-manager wazuh-indexer wazuh-dashboard filebeat
curl -sk -u admin:<password> https://<indexer-ip>:9200/_cluster/health   # from the app host
```

### 2d. If it does not come back

```bash
cp -a /root/opensearch.yml.bak-<timestamp> /etc/wazuh-indexer/opensearch.yml
systemctl restart wazuh-indexer
journalctl -u wazuh-indexer -n 50 --no-pager
```

The journal names the failed bootstrap check explicitly.

### 2e. Firewall it

Port 9200 now answers on your network, and it holds your whole vulnerability inventory.
Restrict it to the app host:

```bash
# nftables / ufw equivalent — adjust to your firewall
ufw allow from <app-host-ip> to any port 9200 proto tcp
ufw deny 9200
```

## Step 3 — alternative: SSH tunnel

Leaves the Indexer on loopback and exposes nothing to the network:

```bash
ssh -N -L 9200:127.0.0.1:9200 root@<wazuh-host>
```

Point patch-tracker at `https://127.0.0.1:9200`. Use `autossh` or a systemd unit so the
tunnel survives reboots. This is the safer option; the cost is a process to supervise.

## Step 4 — create a read-only Indexer user

**Do not give patch-tracker the `admin` account.** It only ever reads. In the Wazuh
dashboard, *Security → Internal users*, create a user, then *Security → Roles* with:

- Cluster permissions: `cluster_composite_ops_ro` (required for the point-in-time
  and composite reads the ingest uses)
- Index pattern: `wazuh-states-vulnerabilities-*` and `wazuh-states-inventory-*`
- Index permissions: `read`
- Tenant: `global_tenant`, read only

Map the role to the user under *Mapped users*. The built-in `readall` user also works
but grants read on **every** index — scope your own role instead.

## Step 5 — configure the app

Bring the app up, log in, and open the **Configuration** tab. Fill in:

| Field | Example | Notes |
|---|---|---|
| Indexer URL | `https://wazuh.example.com:9200` | Or `https://127.0.0.1:9200` for topology A/C |
| Username / password | the read-only user from Step 4 | Stored encrypted; never written to the repo |
| Verify TLS | off for a default install | Wazuh ships self-signed certs whose CN will not match your address |
| Manager API URL | `https://<wazuh-host>:55000` | Optional. On 4.13+ leave it empty: agent IP and Windows hotfixes are read from `wazuh-states-inventory-*` on the same connection |

Press **Test connection**. It reports the cluster status, the Wazuh version and how many
vulnerability documents it can see. A green result means you can switch the data source
from `demo` to `wazuh` and run the first ingest.

## Notes

- **History starts when you do.** The index holds only *currently active* vulnerabilities
  and carries no history — a record disappears when the package is patched. patch-tracker
  derives resolved/reopened by diffing successive ingests, so the trend charts are empty
  on day one and fill in from there.
- **Untriaged records are normal.** Wazuh emits `severity: "-"` and the sentinel
  `score.base: -1.0` (not null, not zero) with `under_evaluation: true` for CVEs NVD has
  not scored yet. These land in the *Untriaged* bucket rather than being dropped, and
  score as CVSS-unknown rather than as a genuine zero.
- **Do not read patch age from `vulnerability.detected_at`.** Wazuh re-indexes a record
  whenever it changes, which resets that timestamp — an SLA clock built on it silently
  restarts. patch-tracker stores its own first-seen date per CVE and agent, which is why
  aging only becomes meaningful after the first ingest.
- **Windows KBs are not in the vulnerability index.** Wazuh uses installed hotfixes to
  *suppress* CVEs: when a KB that fixes a CVE is installed, the record is deleted rather
  than marked resolved. Installed KBs are listed in `wazuh-states-inventory-hotfixes-*`
  (Wazuh 4.13+), or via `GET /syscollector/{agent_id}/hotfixes` on older versions.
- **EPSS and CISA KEV** are fetched from public feeds (FIRST.org, CISA). They are queried
  by CVE identifier only — no information about your infrastructure leaves your network.
  On an air-gapped host, disable them: scoring degrades to CVSS-only automatically.
