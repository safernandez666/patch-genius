How Patch Genius works

What it reads, how it ranks, and why some numbers take a while to mean anything.

Where the data comes from

Patch Genius reads the wazuh-states-vulnerabilities-* index from the Wazuh Indexer. Since Wazuh 4.8 vulnerability data no longer lives in the manager API, so that index is the only supported source.

That index holds only active vulnerabilities: when you patch a package — or install the KB that fixes a CVE on Windows — Wazuh deletes the record. There is no status field and no history.

How it ranks

The same order a SOC analyst would use:

  1. CISA KEV first — confirmed active exploitation in the wild. If a CVE is here, the CVSS matters much less: somebody is already using it.
  2. EPSS next — estimated probability of exploitation within the next 30 days.
  3. Priority score as a single number to sort by:

CVSS × weight + EPSS × weight + bonus when listed in KEV, capped at 100

The weights are environment variables. With no EPSS available the score degrades to CVSS alone rather than penalising the CVE.

Severities

Critical

CVSS 9.0 – 10.0

Exploitable with full impact on the system. Patch these first, especially when also listed in KEV.

High

CVSS 7.0 – 8.9

Serious impact or easy exploitation. Together with criticals, this is the headline number.

Medium

CVSS 4.0 – 6.9

Requires preconditions, or the impact is partial.

Low

CVSS 0.1 – 3.9

Limited impact. Usually fits the normal maintenance window.

Untriaged

no NVD score yet

Wazuh reports these with severity - and under_evaluation. They are not low severity — they are unknown, and a new one can turn out to be critical.

Aging and the patching SLA

Aging counts from the first time Patch Genius saw the CVE, not from the date Wazuh reports.

Wazuh reescribe vulnerability.detected_at cada vez que reindexa un registro, cosa que pasa por motivos internos. Un SLA construido sobre ese campo se reinicia solo y nunca vence: mostraría todo en verde para siempre. Por eso guardamos fecha propia.

The practical consequence: on day one everything shows 0 days. Aging and the SLA only mean something after the app has been running a while. Same for the trend charts — Wazuh keeps no history, so the series is built forward, one snapshot per day.

Resolved, reopened, new

Because the index has no status, each ingest is compared with the previous one:

  • New — the (CVE, agent) pair appears for the first time.
  • Resolved — it was there and is gone. Wazuh deleted the record, so it was patched.
  • Reopened — it was resolved and came back. Usually a rollback, a reinstall, or an old image redeployed.

All of this is tracked per CVE and per agent: the same CVE can be resolved on one server and open on another.

Security

  • Every route requires a login. This screen is the list of what is unpatched on live machines.
  • Wazuh credentials are stored encrypted and never returned to the browser.
  • Use a read-only Indexer account, not admin.
